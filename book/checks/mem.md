# MEM checks, explained

Detail page for the `MEM` category of the [check catalogue](../checks.md#-mem---memory-layout-and-linker). Each
section explains one check: what it catches, why the firmware fails without it, a concrete example, how it is
checked, and the fix. The one-line entries in the catalogue stay the source of truth for ID, severity and wording;
this page is the commentary. Most of these checks are about `memory.x`, generated by `build_layout()` /
`render_memory_x()` in `bedrock_gen.py` — see
[memory-layout.md](../../firmware_template_skill/references/memory-layout.md) for the layout rules themselves.

## `MEM-1` FLASH length covers a region kept for something else <a id="mem-1"></a>

🛑 error · check: cfg mid · [catalogue entry](../checks.md#mem-1)

**What it catches.** `memory.x`'s `FLASH` region sized so the application image can grow into flash that's actually
reserved for settings, the bootloader, or the DFU slot.

**Why it matters.** The linker only enforces the region it's told about; if `FLASH` is sized too generously, an
image that grows past its intended boundary links successfully and overwrites the next region's first bytes at
flash time instead of failing the build.

**Example.** usb_io_fw PLAT-13/PLAT-15: the application region overlapped space meant for settings and bootloader
state.

**How to check.** `cfg mid`: recompute the partition table from `memory-layout.md`'s rules (flash base, sector
sizes, `--bootloader`/`--settings` flags) and compare against the `FLASH` length actually in `memory.x`.

**Fix.** Regenerate `memory.x` from the current flags rather than hand-editing region lengths; if hand-edited,
match the generator's partition order (`BOOTLOADER`, `FLASH`, `BOOTLOADER_DFU`, `SETTINGS`).

## `MEM-2` Extra RAM section with a tail that keeps it non-empty <a id="mem-2"></a>

⚠️ warning · check: cfg easy · [catalogue entry](../checks.md#mem-2)

**What it catches.** An extra RAM output section (one of the `.<name>` sections for a secondary RAM bank) that
carries a trailing `. = ALIGN(n)` or a symbol placed inside it, which keeps lld from dropping the section even when
nothing is actually placed there.

**Why it matters.** lld drops a genuinely empty output section; one with so much as an alignment directive at the
end counts as non-empty, and flip-link 0.1.12 counts that non-empty section — even with zero real content — as
used RAM. At the very end of the RAM map that leaves no room for the stack at all (see `STK-3`).

**Example.** The RP2350's `.sram8` section hit exactly this (embedded_bedrock ROB-12); the fix is already encoded
in `memory-layout.md` ("Notes for manual edits": leave extra-RAM sections without symbols or `. = ...` lines).

**How to check.** `cfg easy`: scan generated/edited linker fragments for a RAM output section with a trailing
`. = ALIGN` or any symbol definition inside it.

**Fix.** Drop the trailing alignment/symbol from sections meant to stay empty when unused; let lld remove them.

## `MEM-3` RAM init/zero range overlapping `.uninit` <a id="mem-3"></a>

🛑 error · check: elf mid · [catalogue entry](../checks.md#mem-3)

**What it catches.** The startup code's RAM-zeroing range (from `init_ram.rs`, per `memory-layout.md`'s "every
other RAM bank gets a `NOLOAD` section ... and zeroes it at boot") overlapping `.uninit` — the section that holds
the crash record or handoff data across a reset.

**Why it matters.** `.uninit` exists specifically to survive a reset unzeroed; if the generic RAM-zero loop's
address range includes it by accident, the crash record from the fault that just happened is wiped before the
next boot can read and report it.

**Example.** Template 0.4: a bank-zeroing range computed from the RAM map's new layout started overlapping
`bedrock_crash`'s `.uninit` section in usb_io_fw's `init_ram.rs` until the ranges were split apart explicitly.

**How to check.** `elf mid`: read both the zeroing loop's address range (from the compiled `init_ram.rs`) and
`.uninit`'s linked address range, and check they don't intersect.

**Fix.** Exclude `.uninit`'s range from any generic RAM-zero loop; it's zeroed only by an explicit factory-reset
path, never at every boot.

## `MEM-4` Extra SRAM bank used before its RCC clock enable <a id="mem-4"></a>

🛑 error · check: src mid · [catalogue entry](../checks.md#mem-4)

**What it catches.** Code that reads or writes a secondary SRAM bank before the RCC enable bit that clocks that
bank has been set.

**Why it matters.** An unclocked SRAM bank doesn't fault cleanly on most STM32 parts; depending on the part it can
read as all-zero, all-one, or genuinely undefined bus noise, which is a confusing failure to trace back to "the
clock wasn't on yet" days after the access.

**Example.** embedded_bedrock TPL-3: this is exactly why `init_ram.rs` is generated to enable each extra RAM
bank's RCC clock (matching `<NAME>EN` fields in the RCC `*ENR` registers per `memory-layout.md` "RAM") before the
zeroing loop touches it.

**How to check.** `src mid`: from the firmware model, every access to a secondary RAM bank's address range must be
ordered after that bank's RCC enable write.

**Fix.** Enable the bank's RCC clock first (the generator's `init_ram.rs` already does this for generated banks);
for a hand-added bank, add the enable before first use.

## `MEM-5` Backup-register map overlap <a id="mem-5"></a>

🛑 error · check: cfg mid + elf mid · [catalogue entry](../checks.md#mem-5)

**What it catches.** The backup-register region (TAMP or RTC `BKPnR`, per `memory-layout.md` "Backup-register
counters") used for more than one purpose at overlapping offsets: the `cnt!` buffer (`CNT_BKP_BUFFER_SIZE_WORDS`
registers), the boot word, the boot reason, and board state all need their own, non-overlapping slice past the
first fixed register.

**Why it matters.** Backup registers survive resets by design, which is exactly why two features sharing the same
register corrupt each other silently — a counter write stomping the boot-reason word (or the reverse) looks like
either feature randomly losing its value.

**Example.** vb135 BOOT-5/BOOT-7, and template 0.4.1's fix: the register map needed an explicit, documented
allocation once more than one feature wanted backup registers.

**How to check.** `cfg mid` (the configured sizes: `CNT_BKP_BUFFER_SIZE_WORDS` and any other backup-register
consumer's declared size) plus `elf mid` (the linked addresses of `.cnt_bkp_buffer` and any other backup-domain
symbol) — the ranges must not overlap.

**Fix.** Give each backup-domain consumer its own fixed offset past the others, documented in one place (the
template's memory-layout notes), not derived independently by each feature.

## `MEM-6` `.cnt_bkp_buffer` not at the backup-register address <a id="mem-6"></a>

⚠️ warning · check: elf easy · [catalogue entry](../checks.md#mem-6)

**What it catches.** The `cnt` crate's `.cnt_bkp_buffer` NOLOAD section linking to an address other than the
backup-register region (`BKPSRAM`/`BKP_REGS`) it was meant to sit in.

**Why it matters.** If `.cnt_bkp_buffer` lands in ordinary RAM instead of the backup domain, every counter it
holds is zeroed on the next reset, which defeats its entire purpose (counting events *across* resets) without any
error — the counters just quietly reset to zero every time.

**Example.** Template 0.3.0: an early version of the counter placement didn't pin the section to the backup
region reliably on every chip.

**How to check.** `elf easy`: read `.cnt_bkp_buffer`'s linked address from the ELF and compare against the chip's
known backup-register address (`BKPR` arrays at `TAMP + 0x100` or `RTC + 0x50`, per `stm32-notes.md` "Backup
domain").

**Fix.** Point `cnt.x`'s section placement at the memory region named in `.cargo/config.toml`'s
`CNT_BKP_MEMORY_REGION` (`BKPSRAM` for the register-array region, `BKP_REGS` on chips with a real backup SRAM).

## `MEM-7` Flash partition symbols written as absolute addresses <a id="mem-7"></a>

⚠️ warning · check: cfg easy · [catalogue entry](../checks.md#mem-7)

**What it catches.** A `memory.x` symbol for an embassy-boot flash partition (`__bootloader_active_start`,
`__bootloader_dfu_start`, ...) given as an absolute flash address instead of an offset from the flash base.

**Why it matters.** `memory-layout.md` ("Symbols") is explicit that these are offsets (`- ORIGIN(FLASH)` /
`- ORIGIN(BOOTLOADER)` / `- ORIGIN(BOOT2)`) because `FirmwareUpdaterConfig::from_linkerfile_blocking` and the
embassy flash drivers read them as offsets, not absolute addresses — an absolute address there is silently
interpreted as an offset and points at the wrong place in flash by however far the flash base sits from zero.

**Example.** Documented directly in `memory-layout.md`'s symbol rules as the reason the generator always subtracts
the region's origin.

**How to check.** `cfg easy`: a bootloader-partition symbol definition in `memory.x` that doesn't include a
`- ORIGIN(...)` subtraction.

**Fix.** Always compute these symbols as `<address> - ORIGIN(<region>)`, matching what the generator emits.

## `MEM-8` Settings store too small, or on the code's bank <a id="mem-8"></a>

⚠️ warning · check: cfg mid, chip table · [catalogue entry](../checks.md#mem-8)

**What it catches.** A settings region smaller than two erase pages (ww_settings compacts into the next page
before erasing one, so it needs at least two), or placed on the same flash bank the running code executes from on
a dual-bank part.

**Why it matters.** Too small and the store can't compact without temporarily needing more space than it has.
Co-located with the running code's bank, an erase during a settings write can stall fetches from that bank for the
whole erase time — on the banks and page sizes `memory-layout.md` lists (STM32G0B1 512K: 4 × 2 KiB pages), that's
a real, user-visible stall right in the middle of normal operation.

**Example.** `memory-layout.md` places `SETTINGS` at the very end of flash specifically so on a dual-bank part it
lands in bank 2 while code typically runs from bank 1; donguru_template needed this worked out explicitly for its
layout.

**How to check.** `cfg mid` plus the chip's bank/page-size table: settings region ≥ 2 erase pages and ≥ 8 KiB, and
(on dual-bank parts) not sharing a bank with the code the running firmware executes from.

**Fix.** Keep settings at the end of flash as the generator does; on parts with large sectors (F4, H7: 128 KiB),
follow the generator's printed note toward the small F4 sectors at the start or an external NOR instead of forcing
a 256 KiB reservation.

## `MEM-9` ROM-bootloader-surviving data kept in RAM the ROM uses <a id="mem-9"></a>

🛑 error · check: elf mid, chip table · [catalogue entry](../checks.md#mem-9)

**What it catches.** Data meant to survive entry into the ROM bootloader (a handoff flag, a boot-mode request)
placed in a RAM region the ROM itself uses as scratch space — on H7, AXI SRAM from `0x24000000` or DTCM from
`0x20004100`.

**Why it matters.** The ROM bootloader isn't aware of the application's data at all; it uses parts of RAM as its
own working space during a DFU session, and anything the application left there is simply overwritten, so a flag
read as "still set" after a ROM session may actually be stale from before it, or the flag the application thought
it set never survives the session.

**Example.** vb135 BOOT-4: a handoff value needed to move out of AXI SRAM/DTCM into backup registers specifically
because the ROM bootloader's own scratch use on H7 overlaps exactly those ranges.

**How to check.** `elf mid` plus a chip table of the ROM's known scratch ranges: any symbol meant to survive a ROM
session must link outside those ranges.

**Fix.** Keep ROM-survival data in backup registers (`MEM-5`), never in general RAM, regardless of how convenient
the address looks.

## `MEM-10` RWX LOAD segment, or a writable symbol in `.rodata` <a id="mem-10"></a>

⚠️ warning · check: elf easy · [catalogue entry](../checks.md#mem-10)

**What it catches.** A LOAD segment in the linked ELF marked both writable and executable, or a `static mut`
symbol that the linker placed inside `.rodata` (a read-only section) rather than `.data`/`.bss`.

**Why it matters.** A `static mut` the linker put in `.rodata` compiles and links without complaint, but any write
to it at run time either faults (on an MPU-protected part) or silently does nothing (flash-backed `.rodata` on
others) — neither is the mutable storage the code was written assuming it has.

**Example.** `cnt`'s `_CNT_SIGNATURE`: a static that needed checking to confirm it actually landed in writable
memory, not folded into `.rodata` by the linker's section merging.

**How to check.** `elf easy`: read each LOAD segment's flags for the W+X combination, and cross-reference known
`static mut` symbols against which output section they actually linked into.

**Fix.** Give the symbol an explicit `#[unsafe(link_section = ...)]` into a writable NOLOAD/data section if the
linker's default placement put it somewhere read-only; split any genuinely RWX segment the linker script produces.

## `MEM-11` Linker warnings ignored <a id="mem-11"></a>

⚠️ warning · check: cfg easy · [catalogue entry](../checks.md#mem-11)

**What it catches.** Section-alignment warnings from the linker going unexamined — the kind that, on RP235x,
flagged `.text` not being 8-aligned after `.start_block`.

**Why it matters.** A misalignment the linker warns about and the tool still produces an image for isn't
necessarily harmless; RP235x's boot path cares about `.start_block`'s alignment specifically, and ignoring the
warning there produced a real bug, not just noise (template 0.4.3).

**Example.** Template 0.4.3's fix came directly from reading a linker warning instead of treating the build as
clean because it still produced an ELF.

**How to check.** `cfg easy`: capture the linker's stderr during a release build and fail on any warning rather
than discarding it.

**Fix.** Treat linker warnings as build failures until each one is understood and explicitly accepted (with a
comment saying why), the way template 0.4.3 now does for `.start_block` alignment.

## `MEM-12` defmt without `-Tdefmt.x` <a id="mem-12"></a>

🛑 error · check: cfg easy + elf easy · [catalogue entry](../checks.md#mem-12)

**What it catches.** `defmt`/`defmt-rtt` in the dependency tree without `-Tdefmt.x` passed to the linker, so no
`.defmt` section is produced.

**Why it matters.** Without `.defmt`, the interned format strings defmt needs to decode RTT output at the host
side don't exist in the image; probe-rs (or any defmt decoder) either refuses to attach meaningfully or shows
nothing recognisable, and the failure looks like "logging isn't working" rather than "the linker argument is
missing".

**Example.** Documented in [book/issues.md](../issues.md) as a recurring first-boot surprise on a freshly
hand-edited `.cargo/config.toml`.

**How to check.** `cfg easy` (defmt present in `Cargo.toml` implies `-Tdefmt.x` must be in `rustflags`) plus
`elf easy` (confirm `.defmt` actually exists in the linked output).

**Fix.** Add `-C link-arg=-Tdefmt.x` to the target's `rustflags` in `.cargo/config.toml`; the generator always
includes it when defmt is selected.
